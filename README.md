# Techlance Academy

The public website, student LMS, and admin dashboard for Techlance Academy —
built with Next.js (App Router), TypeScript, Tailwind CSS, and Supabase.

This README covers **Phase 1 (foundation, design system, theming) and
Phase 2 (database schema)** only. See the phase list at the bottom for
what's next.

## Stack

- Next.js 16 (App Router) + TypeScript
- Tailwind CSS v4 (class-based dark mode)
- shadcn/ui-style components (hand-authored, Radix primitives underneath)
- next-themes (light / dark / system, no flash)
- Supabase (Postgres, Auth, Storage, Row Level Security)
- React Hook Form + Zod
- Inter Variable + Inter Tight Variable (via `@fontsource-variable`)

## Getting started

```bash
npm install
cp .env.example .env.local   # then fill in your Supabase project values
npm run dev
```

The site runs and is browsable **without** Supabase configured — the public
marketing pages don't depend on it yet. Anything under `/student` or
`/admin` will redirect to its login page (and login will only ever succeed
once real Supabase credentials are set, since there's no way to sign in
without a real project).

## Setting up Supabase

1. Create a project at [supabase.com](https://supabase.com).
2. In the SQL Editor, run every file in `supabase/migrations/` **in
   filename order** (001 → 013). They're written to be idempotent
   (`if not exists` / `on conflict do nothing`), so re-running them is safe.
3. Copy your Project URL, anon key, and service role key from
   *Project Settings → API* into `.env.local` (see `.env.example`).
4. Create your first admin account (there's no self-serve admin sign-up by
   design — see below).

### Creating the first admin

There's no public "sign up as admin" flow on purpose (see spec section 62).
To create the first admin:

1. Create a user the normal way — either through Supabase Auth (dashboard →
   Authentication → Add user), or by having them sign up once a public
   student registration flow exists (Phase 4).
2. This automatically creates a matching row in `public.profiles` with
   `role = 'student'` (see the `handle_new_user()` trigger in
   `002_identity.sql`).
3. Promote that row to admin using the **service role** key (this
   intentionally can't be done with the anon key/RLS):
   ```sql
   update public.profiles set role = 'admin' where email = 'you@example.com';
   insert into public.admins (id) select id from public.profiles where email = 'you@example.com';
   ```
4. Sign in at `/admin/login`.

### How students get created (once Phase 3/4 land)

`applications` (public form) → admin reviews in `/admin/applications` →
admin approves → admin creates the Supabase Auth user + `students` row
(server-side, via the service-role client) → student receives login access
→ student is enrolled into a program (`enrollments`) → student sees their
dashboard. The database structure for all of this already exists; the
admin-side UI to drive it is Phase 6.

### How certificates get issued (once Phase 7 lands)

An admin issues a certificate from `/admin/certificates` for a
student + program. This inserts a row into `certificates` with a unique
`certificate_code` and `verification_code` (generated by the database).
Anyone can then check it at `/certificate-verification`, which calls the
`verify_certificate()` Postgres function — a `SECURITY DEFINER` RPC that
returns only the public-safe fields and logs the lookup, without ever
exposing the full `certificates` table to anonymous users.

## What's implemented (Phase 1 + 2)

- Full design token system (light / dark / system theme), Tailwind v4
  `@custom-variant dark`, no-flash theme switching, Sun/Moon/Monitor toggle
- Typography: Inter Variable (body/UI) + Inter Tight Variable (display)
- Reusable UI primitives: Button, Card, Badge, Input, Label, Separator,
  Avatar, Sheet, DropdownMenu
- Responsive public Navbar + Footer, mobile drawer navigation
- Homepage (hero, value props, final CTA) + structural stub pages for every
  other public route named in the spec (Programs, Program detail,
  Admissions, Apply, About, FAQ, Contact, Blog, Blog post, Certificate
  Verification, Resources, all 7 policy pages)
- Full student and admin route structures, each with its own sidebar +
  topbar shell, built on a shared `DashboardShell` component
- Working Supabase Auth wiring for `/student/login` and `/admin/login`
  (real server actions calling `supabase.auth.signInWithPassword`, with a
  role check against `profiles.role`) — untestable until you connect a real
  Supabase project, but not placeholder code
- Server-side route protection: the student/admin portal layouts are
  Server Components that check the session + role via `lib/auth.ts` and
  redirect if it doesn't match, rather than hiding links client-side
- Complete Postgres schema (`supabase/migrations/001`–`010`): profiles,
  students, admins, instructors, applications, enrollments, programs,
  program_modules, courses, lessons, learning_materials, classes,
  class_attendance, assignments, assignment_submissions, quizzes,
  quiz_questions, quiz_options, quiz_attempts, student_progress,
  certificates, certificate_verifications, announcements,
  announcement_targets, notifications, faqs, testimonials,
  blog_categories, blog_posts, resources, contact_messages, site_settings,
  site_content, audit_logs
- Row Level Security on every table (`011_rls_policies.sql`), plus three
  `SECURITY DEFINER` RPC functions where a plain row policy either isn't
  enough or would leak data: `verify_certificate()`, `get_quiz_questions()`
  (strips `is_correct` before it reaches the browser), and
  `submit_quiz_attempt()` (grades server-side)
- Storage buckets + policies (`012_storage.sql`) for avatars, program
  images, blog images, resources (all public-read), and course materials,
  assignment submissions, and certificates (all private/owner-scoped)
- Realistic seed data (`013_seed_demo_data.sql`) — 10 real programs, FAQs,
  demo testimonials clearly flagged `is_demo = true`, demo blog posts,
  homepage stats flagged `"is_demo": true` in their JSON payload
- Hand-authored `types/database.types.ts` matching the schema exactly

## What's intentionally *not* built yet

Every interior page beyond the homepage is a clean structural stub (real,
on-brand copy describing what the page will contain — no "Coming Soon"
boxes, no lorem ipsum, no dead buttons) rather than a fully data-wired
feature. That's deliberate: the person who owns this project asked to
review the foundation before building on top of it. The original 10-phase
plan has this as Phases 3 through 10 — the full admissions form and public
program/blog content, LMS data views, admin CRUD screens, certificate
generation, and final security/performance/responsive passes.

## Known limitations to revisit

- `middleware.ts` uses Next's (deprecated-but-supported) middleware
  convention rather than the newer `proxy.ts` naming Next 16 suggests —
  works today, worth migrating later (`npx @next/codemod@canary
  middleware-to-proxy .`).
- `course-materials` storage bucket policy is authenticated-read rather
  than scoped to "enrolled in the right program" — the real gate is meant
  to be signed URLs issued only after the `learning_materials` RLS check
  passes, once the upload/download flow is built in Phase 5.
- `database.types.ts` is hand-written to match the SQL exactly, but should
  be regenerated from the live database once Supabase is connected:
  `npx supabase gen types typescript --project-id <ref> > types/database.types.ts`.
